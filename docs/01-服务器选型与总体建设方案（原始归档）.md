# 满语文数智化平台 · 服务器选型与总体建设方案

> 项目：通化师范学院 吉林省满语文数智化开发及沉浸式体验平台
> 编制时间：2026-09-15
> 文档性质：总体方案（非详细设计），用于选型决策、汇报与立项

## 前提与定位（**务必先读**）

### 本平台第一版的定位是「演示平台」

服务场景：

- 给**领导汇报**、项目**验收**、**会议演示**、参观接待
- 校外/线上展示（因此**必须**部署在**外网云服务器**，校内路线已作废）

### 明确不纳入本期范围

| 不做的 | 放在哪里 |
|---|---|
| 生产级的批量处理（大规模 OCR 批处理、语料批量生成） | **实验室工作站** |
| 模型训练 / 微调 / 调参 | **实验室工作站** |
| 高并发在线服务、SLA 保障 | **本期不考虑** |

> 一句话：**工作站负责"干活"，云端只负责"好看、点得动、看得见推理过程"。**

### 由此推出的两个核心结论

1. **默认不买 GPU。** 演示场景下一台 **CPU 云服务器** 即可：
   - 走 **轻量应用服务器 4核8G**（含带宽 + 流量包）→ **约 1,100 ~ 1,600 元/年**
   - 走 **ECS 经济型 e 8核16G**（包年 2,954.88 + 200G 云盘 840 + 按流量带宽约 300）→ **约 4,150 元/年**
   - ⚠️ 注意：**阿里云轻量没有 8核16G 档位**，要 8核16G 只能走 ECS。
2. **演示成败的关键不是算力，而是"不能卡"。** 靠**预生成结果缓存 + 演示模式开关**解决，而不是靠硬件堆（详见 3.6）。

## 0. 结论速览（TL;DR）

| 问题 | 结论 |
|---|---|
| 定位是什么？ | **演示平台**：给领导汇报、开会、验收、参观。**不承担生产、不做批处理**，那些都在实验室工作站上。 |

| 三个省钱开关 | **包年**（别月付，省 880 元）· **带宽按流量**（别买 5M 固定带宽，省 1,000 元）· **云盘只买 100~200G**（500G 多花 1,260 元） |
| 上线硬前置 | **自购域名 + ICP 备案（需云服务器剩余时长 ≥ 3 个月）**，务必提前 3~4 周启动 |
| 架构关键 | **全部容器化（Docker Compose）+ 配置外置 + 数据与代码分离**，保证"工作站跑通的东西能原样搬到云端" |

### 1.4 已有架构图的构想（来自 PDF）

PDF 中已规划四条业务路径：

1. **知识图谱模块**：图谱构建、实体关系抽取、知识可视化、智能查询
2. **机器翻译模块**：满汉双向翻译引擎、译文质量评估
3. **语音路径**：语音识别（满/汉/英输入 → 识别文本输出）、语音合成（文本规范化 → 标准满语语音生成 → 音频输出）
4. **语料库与语言学分析路径**：词干-附加成分拆分、自动词法分析、语法标注系统、句法树生成、语言学检索引擎、学术引用系统
5. **在线阅读与出版路径**：双文对照引擎、交互式阅读、点词联动高亮、调原文图像、画词词典查询、导出 PDF/EPUB/Word

数据层：文献图像库、满文文本数据库、满语词典数据库、语料标注数据库、知识图谱数据库
入口层：Web/PC、移动端 App、第三方 API 接口

> 本方案在该架构基础上，**补充"统一门户/聚合层"与"工作站→云端的部署路线"两个原图未展开的关键部分**，并重点设计用户提出的"推理过程可视化"。

## 二、服务器选型建议（腾讯云 / 阿里云买什么）

### 2.1 演示场景下的负载判断（结论：一台 CPU 机器全包）

| 负载类型 | 组成 | 演示场景下对硬件的要求 |
|---|---|---|
| **A. 门户与业务负载** | 静态页面、登录、语料元数据、页面渲染、示例数据 | 吃 CPU/内存/磁盘 IO，**不需要 GPU**；4~8 核即可 |
| **B. 模型推理负载** | OCR、翻译、TTS、ASR | **演示场景下可被"预生成结果 + 缓存"大幅替代**，只有"现场展示推理过程"时才真跑 |

> 因为**生产与批处理都在工作站上**，云端只承担演示，所以**两类负载可以合并到一台 CPU 服务器**——不需要拆机，也不需要 GPU。
> 判断依据：演示时真正会同时操作的人只有几位到十几位，且绝大多数点击会命中缓存。

### 2.2 部署形态：工作站"干活"，云端"演示"（两段式）

根据最新确认：**学校服务器路线完全不可行**——校内既无法对外网开放，也无法在校内架设对外服务。

```
① 实验室工作站（干活的地方，本期不规划）        ② 外网云服务器（演示的地方，本期重点）
   ├─ 模型训练 / 微调 / 调参                      ├─ 门户 + 6 大功能页（常开）
   ├─ 批量处理（OCR 批量、语料批量生成）            ├─ 预生成结果缓存（常用操作秒回）
   ├─ 真实推理（完整模型 / 大模型）                 ├─ 少量真实推理（只为展示"推理过程"）
   ├─ 开发与前端联调                              ├─ 对象存储 + 轻量数据库
   └─ 产出：镜像 + Compose + 预生成结果包           └─ 交付：一个"点得动、看得见"的站点
        └───────── 镜像 / Compose / 预生成结果 一起搬过去 ─────────┘
```

| 环境 | 定位 | 本期要求 |
|---|---|---|
| 实验室工作站 | 生产 / 训练 / 批量 / 开发 | **本期不纳入规划**，按现有条件使用即可 |
| 外网云服务器 | **演示专用** | 优先"稳、快、好看"，**不追求并发与吞吐** |
| 工作站 → 云端 | 交付方式 | 镜像 + Compose + **预生成结果包（缓存）** 一起搬过去 |

### 2.3 服务器角色划分建议（演示版：一台机器全包）

```
┌─────────────────────────────────────────────────────────┐
│ ① 唯一的云服务器（CPU 型，8核16G，常开）                  │
│    承担：Nginx 网关 + 门户前端 + 业务 API +               │
│          PostgreSQL + Redis（结果缓存） + 轻量推理        │
│    ★ 不需要 GPU                                          │
├─────────────────────────────────────────────────────────┤
│ ② 对象存储 OSS/COS（按量，极便宜）                        │
│    承担：古籍图像、音频、语料样例、预生成结果、备份         │
├─────────────────────────────────────────────────────────┤
│ ③ 域名 + SSL + 备案（成本极低，但时间成本高）              │
└─────────────────────────────────────────────────────────┘
```

> （原方案中"① 应用服务器 + ② GPU 推理服务器"的拆机方案，**演示版不需要**；若将来要做真正的对外服务，再按 2.5 的备选方案加 GPU。）

### 2.4 演示场景下，纯 CPU 云服务器够不够？（答：够）

**结论先给：够。** 但必须理解"够用"的前提——**不是靠算力，而是靠"预生成 + 缓存 + 进度反馈"**。

先看纯 CPU 的真实性能（参考值，取决于模型大小与 CPU 型号）：

| 模块 | 纯 CPU 可行性 | 实际表现 | 演示会不会翻车 |
|---|---|---|---|
| 满文 ⇄ 拉丁互转 | ✅ 完全可行 | 纯规则计算，毫秒级 | 不会 |
| 语料集（浏览/检索/下载） | ✅ 完全可行 | 普通 Web 应用 | 不会 |
| 满文 OCR | ⚠️ 慢但可用 | 单张小幅图约 1~5 秒；批量 1,000 张需几十分钟到数小时 | 不会（单张可接受） |
| 语音合成 TTS | ⚠️ 能出音但很慢 | GPT-SoVITS 约 **10~60 秒/句**（GPU 约 0.3~2 秒） | 有风险 → 用预生成音频规避 |
| 语音识别 ASR | ⚠️ 短音频可用 | Whisper base/small 约 0.5~3 倍音频时长 | 有风险 → 用预置音频规避 |
| **满汉翻译（LLM）** | ❌ 大模型不可行 | 27B 约 1~3 token/s，一句话几十秒到几分钟；7B-INT4 约 5~15 token/s | **唯一真正会翻车的点** |

**演示场景的规避方案（这是本方案的核心技巧）：**

| 模块 | 演示时怎么处理 | 观感 |
|---|---|---|
| 互转、语料集 | 直接真跑 | 秒回 |
| OCR | 预置 3~5 张经典古籍图（结果提前跑好）；现场若上传新图则真跑 + 进度条 | 预置的秒回，新图 3~10 秒 |
| TTS | 预生成 3~5 段示例音频；现场输入则真跑 + SSE 进度条 | 预置的秒回，新输入 10~30 秒（有进度条可接受） |
| ASR | 预置 2~3 段音频样例；现场录音则真跑 | 同上 |
| **翻译** | **预置 10~20 条经典句对**（可直接用现有语料样例）；现场输入走小模型或"演示模式" | 预置的秒回 |

**三个要说清楚的点：**

1. **慢是事实，但演示可以规避。** 只要把"领导最可能点的内容"提前预生成好，观感就是"秒回"。真实推理只在"展示推理过程"这一环节触发，且有进度条兜底。
2. **并发在演示场景下不是问题。** 开会时同时操作的人很少，且大多命中缓存；不像生产环境那样需要扛住批量请求。
3. **唯一真正会翻车的是"现场让 27B 大模型做翻译"。** 建议：现场演示避免触发大模型真推理；确实需要时提前 5 分钟预热一次（首次加载最慢，之后有缓存）。

**两个可选做法：**

| 情形 | 做法 | 成本 |
|---|---|---|
| **演示为主，不现场跑大模型**（本期默认） | **纯 CPU 服务器** | 1,500 ~ 5,000 元/年 |
| 一定要现场演示 27B 真推理 | 在上述基础上**临时加一台按量 GPU**（A10 24G）：演示前 30 分钟开机、结束后立刻关机 | **按量约 4~10 元/小时，一次演示几十元**，用完即停 |

> **演示版必须配齐这三样（比买 GPU 重要得多）：**
>
> 1. **预生成结果缓存**：把常用示例的输入/输出提前算好，存进 Redis 或对象存储，命中即秒回。**这是性价比最高的一件事。**
> 2. **SSE 进度反馈**：真跑的请求全部流式返回"正在执行第 3 步：音素预测…"，让等待"看得见"。——正好和"推理过程可视化"是同一套技术，一举两得。
> 3. **演示模式开关**：一个隐藏开关，可把所有真推理切到"预置结果"，用于现场兜底（机器或网络出问题时不至于开天窗）。

> **补充**：CPU 方案对规格有要求——优先选**支持 AVX-512、主频高、内存带宽好**的规格（阿里云 g8i / 腾讯云 SA3），不要选老架构；内存建议 ≥ 2 倍模型体积；CPU 上跑 LLM 必须用 GGUF / `llama.cpp` 量化，**`vLLM` 在纯 CPU 上基本不可用**。

### 2.5 （备选）若哪天要现场跑大模型：显存测算

| 模型 | 规模 | 显存需求估算 | 说明 |
|---|---|---|---|
| OCR 检测 | 小模型 | 2~4 GB | 版面/文本框检测 |
| OCR 识别 | 中模型 | 3~6 GB | 竖排满文识别 |

| 翻译 LLM | **7B 级** | FP16 ≈ 14GB / **INT4 ≈ 5GB** | 若实际是小模型，16G 卡绰绰有余 |
| TTS (GPT-SoVITS) | 小 | 3~5 GB | 推理很轻 |
| ASR | 中 | 3~6 GB | Whisper 类模型 |

- **L20 48GB**：27B 用 INT8 可跑、并发更好，其余模块可同时常驻 → 舒适档。
- **A100 40GB / 2×L20**：多用户并发、批处理标注、模型训练时才需要。
- **演示版的建议**：**本期不买 GPU。** 若确需临时跑大模型，**按量租一台 A10 24G，演示前开机、演示后关机**即可（约 4~10 元/小时）；只有确定要做长期对外服务时才考虑包月。

### 2.9 预算：5,000 元以内够不够？（答：够，而且用不满）

**直接回答：5,000 元/年以内，对"纯演示版"完全够。**

- 走**轻量应用服务器**（4核8G，含带宽+流量包）：**约 1,100 ~ 1,600 元/年**
- 走 **ECS 经济型 e**（8核16G，包年 + 按流量带宽 + 200G 云盘）：**约 4,150 元/年**

> **关键前提：服务器一定要选"包年"，带宽一定要选"按使用流量"。** 这两条能把 ECS 方案从 5,200 元压到 4,150 元；反之如果月付 + 5M 固定带宽，就一定超预算。

| **② 推荐** | **ECS 经济型 e 8核16G 包年 2,954.88** + 云盘 200G 约 840 + **按流量计费约 300** + 域名 60 | **约 4,150 元** | ✅ **要 8核16G 就选这个，卡在 4,000 出头** |

#### 2.9.2 云盘：200G 够不够？（答：够，500G 纯属浪费）

演示版的真实磁盘占用：

| 用途 | 估算占用 |
|---|---|
| 操作系统 + 基础软件 | 15 ~ 25 GB |
| Docker 镜像（含 PyTorch CPU 依赖） | 15 ~ 30 GB |
| PostgreSQL（演示数据） | 2 ~ 5 GB |
| 预生成结果（音频 / 图片 / JSON） | 1 ~ 5 GB |
| 日志 / 临时文件 / 上传缓存 | 5 ~ 10 GB |
| **合计** | **约 40 ~ 75 GB** |

**结论：100G 够用，200G 宽裕，500G 没必要。**

| 云盘容量 | 年费用（ESSD Entry 0.35 元/GiB/月） |
|---|---|
| 100G | 约 420 元 |
| **200G** | **约 840 元** |
| 500G | 约 2,100 元 ← **多花约 1,260 元/年** |

**两条铁律：**

1. **语料、图像、音频、模型权重一律放 OSS，不要放云盘。**
   OSS 标准型约 **0.12 元/GB/月**，比 ESSD Entry（0.35 元/GiB/月）便宜近 3 倍，而且**内网读取不计公网流量**。
   云盘只放"操作系统 + 代码 + 数据库 + 日志"。
2. **云盘只能扩、不能缩。** 先买 100~200G，不够随时在线扩容，**永远不会亏**。

> ⚠️ **唯一例外**：如果模型权重不想上传 OSS（保密/合规原因），要先算清权重总量。OCR + TTS + ASR + 小翻译模型通常在 **5~30 GB**，仍可放在 200G 内；若是完整大模型（几十 GB 起），才是需要考虑加大云盘的场景——但演示版本来就不上大模型。

### 2.10 选型结论（演示版）

> **① 定位决定选型：这是演示平台，不是生产系统。** 生产与批处理都在工作站上，云端只负责"点得动、看得见"。
> **② 要 8核16G 就买 `ECS 经济型 e` 并选"包年"（¥2,954.88/年）**；只想最省钱就买**轻量 4核8G**（含带宽+流量包，约 1,000~1,600 元/年）。
> 　注意：**阿里云轻量目前没有 8核16G**，需要 8核16G 只能走 ECS。
> **③ 带宽选"按使用流量"（0.8 元/GB）**，不要买 5M 固定带宽（1,380 元/年）。ECS 的带宽是**单独收费**的，报价页上那个价格不包含它。
> **④ 云盘买 100~200G 就够**，500G 是浪费。**语料/图像/音频/模型权重全部放 OSS**（比云盘便宜近 3 倍），云盘只放系统与数据库。
> **⑤ 经济型 e 是"共享型"实例**（非绑定 CPU 调度，性能会被同宿主邻居影响）。演示场景可接受，但**这让"预生成缓存"变得更必要**——CPU 推理本来就慢，不能再叠加性能抖动。预算允许可换 `通用算力型 u1`（贵约 1,270 元/年）。
> **⑥ 本期不买 GPU。** 若某次一定要现场演示大模型真推理，**按量租一台 A10 24G，用完即停，一次几十元**。
> **⑦ 演示效果的决定因素是"预生成缓存 + SSE 进度反馈 + 演示模式开关"这三件事，不是硬件。**
> **⑧ 域名与 ICP 备案是上线硬前置，务必第一周就启动**，否则服务器买好了也开不了站。**

## 三、总体设计思路

### 3.1 设计原则

| 原则 | 落地做法 |
|---|---|
| **P1 一个门户，多个功能** | 统一导航/页头/页脚/设计系统；7 个独立 HTML 收编为同一站点的路由 |
| **P2 松耦合、可插拔** | 每个能力 = 一个独立容器 + 一个 REST/SSE 接口；模型换了不影响门户 |
| **P3 一份镜像，两处运行（硬要求）** | 全部 Docker 化、配置走 `.env`、数据走存储抽象层（MinIO ↔ OSS 一键切换）、无绝对路径。**工作站上跑通的 Compose，云端只改 `.env` 即可启动** |
| **P4 演示友好 / 优雅降级** | 模型不可用时返回预置样例结果 + 明确标识"演示数据"，永不白屏（对应 C8） |
| **P5 过程的可见性** | 所有 AI 能力统一输出**结构化"推理轨迹"**，前端统一渲染（对应"推理过程"需求）；**同时也兼作 CPU 慢速方案下的进度反馈** |
| **P6 数据即资产** | 标注/校对结果统一入语料库并版本化，可随时导出用于再训练 |
| **P7 对外可用 / 弱依赖** | 第三方库全部本地化、字体内嵌；**不依赖任何校内网络资源**，服务全部部署在公网云上，校外可直接访问 |

### 3.3 统一门户（聚合层）设计要点

这是"综合门户"的落点，需要专门做一层：

### 3.4 七大功能模块设计要点

#### 3.4.1 满文古籍 OCR
- **保留**现有交互：上传（单张/多张/批量）、正楷识别、古籍识别、识别汉字、列图显示、字号调节、导出。
- **改造**：
  - 后端地址由 `localhost:1000` / `localhost:7860` 改为网关相对路径 `/api/ocr/...`，由网关转发；
  - 把"检测框"与"识别文本"两段结果**同时回传**，用于推理过程可视化（见 3.5）；
  - 批量任务改为**异步任务 + 进度轮询/SSE**，避免长连接超时。
- **推理过程可视化**：原图 → 版面分析/文本框检测 → 逐列切分 → 单字/字符识别（置信度热力）→ 传统满文输出 → 可选转拉丁。

#### 3.4.2 传统满文 ⇄ 拉丁满文双向转换
- 现有实现是**纯前端规则引擎**，规则量不大、性能可接受 → **保留，但要重构**：
  - 规则表抽为独立 JSON（`rules/manju2latin.json`、`rules/latin2manju.json`），支持后台可视化编辑与版本管理；
  - 支持 Möllendorff / Abkai 等多种罗马化方案切换（预留）；
  - 零宽字符/字位选择（词中、词首、词尾形态）要显式处理并可视化说明。
- **推理过程可视化**：字符级 diff —— 高亮"原始字符 → 命中规则 → 输出字符"，让人看见规则是怎么起作用的。

#### 3.4.3 满汉双向翻译
- 现有为**三模型并列**（本地端口 + `Qwen3.6-27B`），保留"三模型对照"的展示形式（很有说服力）。
- **改造**：
  - 模型调用统一走推理网关（OpenAI 兼容 `/v1/chat/completions`），端口不暴露给前端；
  - 引入 **术语库/词典约束**（满语词典数据库）+ **RAG 检索相似句对**（从 98,038 行语料中召回），显著提升质量；
  - 增加**译文质量评估**（BLEU/chrF 对参考译文、或 LLM 自评打分）——对应架构图中的"译文质量评估"。
- **推理过程可视化（重点）**，建议分 6 步展示：
  1. 输入分词/切分（满文词干—附加成分拆分）
  2. 词法/形态分析（格、数、时、态标注）
  3. 依存句法（可复用 `manchu_ud_annotator` 的 SVG 渲染）
  4. 术语/句对检索命中（展示召回参考译文及相似度）
  5. 模型逐 token 生成（**流式 SSE**，可见思考过程）
  6. 后处理、打分与候选对比
- **降级**：模型未加载时给出静态示例翻译并标注"演示"（对应 C8）。

#### 3.4.4 语音合成（TTS）
- 现有为 **GPT-SoVITS 的 Flask 页面**（`{{ project_title }}` + `/static/app.js`），已实现"拉丁→传统满文同步显示"。
- **改造**：模板拆分为静态页 + 网关 API（`/api/tts/synthesize`）；**结果落对象存储**返回 URL（现有页面已是 `audioUrl` 形式，天然适配）；保留并强化满文同步高亮。
- **推理过程可视化**：原文 → 文本规范化（数字/缩写/标点）→ 拉丁转写 → 音素序列 → 音高/时长预测 → **梅尔频谱图**（现有页面已有频谱图位）→ 声码器 → 音频波形。前端用 ECharts/Canvas 逐层展示。

#### 3.4.5 语音识别（ASR）—— 全新开发
需求明确："目前没做任何东西，要布置好一个好似有东西的页面"。
- **页面能力（先上）**：在线录音（`MediaRecorder`）+ 上传音频 → 返回**拉丁满文** → 依据规则（复用 3.4.2 的规则引擎）**自动转传统满文**，二者同步显示。
- **后端**：优先用公开 Whisper 类模型做**中文/满语转写占位**，用 2,292 条数据做微调（后续）。
- **推理过程可视化**：波形 + 频谱 → VAD 分段 → 声学模型**逐帧后验/置信度时间轴** → CTC 解码候选 → 拉丁转写 → 规则转满文。**"逐帧置信度热力条"是最能体现"AI 在工作"的组件。**

#### 3.4.6 语料集
- 首页卡片展示 5 类语料（数量见 1.5），点击进入详情。
- **详情页统一结构**：数据说明 + 规模统计 + **样例在线浏览**（表格/双行对照/图像网格）+ 下载（受权限控制）。
- **管理能力**：数据集版本（`数据集 → 版本 → 文件` 三级模型）、标注状态统计、导出格式（JSONL/TSV/CoNLL 等）、训练/验证/测试集切分记录。
- 原始文件放**对象存储**，数据库只存元数据与索引（对应 P3、C1）。

#### 3.4.7 工作平台（需登录，不对外）

> **本期定位：只做"能看、能讲"的程度，不做完整工作流。**
> 演示时它承担的是"展示数据闭环能力"的讲述角色（我们有权限体系、有标注、有审核、有入库），**不要求现场真跑一遍标注 → 审核 → 入库**。完整实现放到将来做生产版时再做。


- **OCR 数据标注**：保留现有画框/纠错交互；新增 ①登录与角色（标注员/审核员/管理员）②任务分配 ③审核工作流（待标注 → 已提交 → 审核中 → 已通过/驳回）④**审核通过一键入库**（写入语料库 + 触发版本快照）⑤操作审计日志。
- **满汉双行校对**：**建议重写**（现有版本已知极慢）。重写要点：虚拟滚动（只渲染可视行）、Web Worker 做 diff 与校验、增量 DOM 更新、上万行不卡；支持**原位即时编辑**并自动保存草稿。
- **依存语法可视化**：现有 SVG 方案基本可用，做风格统一 + 支持保存标注结果入语料库。
- **权限模型**：`游客 < 注册用户 < 标注员 < 审核员 < 管理员`；按栏目 + 数据集维度授权。

### 3.5 "推理过程可视化"专项设计（本次需求的核心亮点）

用户明确要求：**满汉翻译推理过程、合成推理过程、识别推理过程**。建议做成**全站统一的"推理轨迹面板"（Inference Trace Panel）组件**，一次开发、三处复用。

**统一数据结构（后端返回 / SSE 推送）**：

```json
{
  "trace_id": "trace_20260915_xxx",
  "task": "translate | tts | asr | ocr",
  "status": "running | done | failed | fallback",
  "steps": [
    {
      "index": 0,
      "key": "segment",
      "title": "分词与形态分析",
      "status": "done",
      "duration_ms": 128,
      "summary": "切分 12 个词，识别 3 处格附加成分",
      "payload": { "tokens": ["...", "..."], "tags": ["..."] },
      "view": "token-list | table | barchart | spectrogram | waveform | text-diff | heatmap"
    }
  ],
  "final": { "text": "...", "audio_url": "...", "score": 0.78 },
  "meta": { "model": "Qwen3.6-27B", "device": "cuda:0", "is_demo": false }
}
```

**前端渲染**：按 `view` 字段选择渲染器（时间轴 + 可折叠步骤卡片），支持"逐步播放/单步查看/一键展开全部/查看原始 JSON"。

| 任务 | 步骤链（steps.key） |
|---|---|
| 翻译 `translate` | `normalize → segment → morphology → syntax → retrieve(术语/句对) → llm-stream → postprocess → score` |
| 合成 `tts` | `normalize → latinize → phonemize → prosody(F0/时长) → acoustic(mel) → vocoder → waveform` |
| 识别 `asr` | `load → vad → feature → acoustic-frame-posterior → ctc-decode → latin-text → manju-script` |
| OCR `ocr` | `load → layout → box-detect → column-split → char-recognize(conf) → manju-text → (optional)latin` |

**技术要点**：
- 长耗时任务用 **SSE（Server-Sent Events）** 推送步骤事件（比 WebSocket 简单、够用、易穿透代理）；
- 每个步骤**必须带 `duration_ms`**，"耗时条"能直观体现引擎在工作；
- 失败/降级时 `status=fallback` 并高亮提示，避免"看起来卡住了"（对应 P4）；
- 中间产物（频谱、热力图、波形）由后端生成 PNG/JSON，**不要在前端重算**，保证低端设备流畅。

### 3.6 演示保障设计（**本期落地重点，优先级高于任何性能优化**）

这一节是"演示版"与"生产版"最大的区别，也是本期最该投入精力的地方。

#### 3.6.1 三层保障

| 层级 | 做法 | 解决什么问题 |
|---|---|---|
| **第一层：预生成缓存** | 上线前把所有"会被点到的示例"跑一遍，输入输出存进 Redis / 数据库；页面默认展示示例，"试一试"直接读缓存 | 90% 的演示操作**秒回** |
| **第二层：SSE 进度反馈** | 真跑的请求流式返回步骤事件（第 1 步…第 3 步…），前端渲染进度 | 剩下 10% 的真推理**不会显得卡死** |
| **第三层：演示模式兜底** | 一个开关（URL 参数或后台），把所有真推理强制切到预置结果 | 现场断网 / 模型挂掉时**不开天窗** |

#### 3.6.2 必须预生成的内容清单

| 模块 | 预生成内容 | 数量建议 |
|---|---|---|
| 满文 ⇄ 拉丁互转 | 无需预生成（纯规则，本身就快） | — |
| OCR | 经典古籍图 + 识别结果 | 3~5 组 |
| 满汉翻译 | 经典句对（可直接用 `all1+2+3.txt` 里的样例） | 10~20 组 |
| 语音合成 | 示例文本 + 音频 + 频谱图 | 3~5 组 |
| 语音识别 | 示例音频 + 识别结果 | 2~3 组 |
| 语料集 | 每类语料的样例数据 | 各 20~50 条 |

> **这些内容的来源就是工作站**：在本地用真模型跑一遍，导出成 JSON + 音频文件，随镜像一起部署到云端。**这就是"工作站干活、云端演示"的具体落地方式。**

#### 3.6.3 演示前检查清单（开会前 30 分钟）

```
□ 所有预生成内容已加载，逐一点击验证
□ 检查对象存储 / Redis 正常，缓存命中生效
□ 真推理路径各测一次，确认进度条正常
□ 按需打开"演示模式"开关
□ 准备纯静态兜底页（本地 HTML + 录屏），断网也能放
□ 确认域名可访问、证书未过期
```

#### 3.6.4 现场演示动线建议

```
门户（讲整体定位）
  → 语料集（讲数据积累）
  → OCR（传一张古籍图，看识别结果 + 推理过程）
  → 翻译（点预置句对，秒回；再展开推理过程面板）
  → TTS（点预置文本出音频 + 频谱，同步显示满文）
  → ASR（放示例音频，看逐帧置信度 → 拉丁满文 → 传统满文）
  → 工作平台（讲数据闭环与权限，可不实际点操作）
```

> **动线原则：先用缓存内容建立"快"的印象，最后才展示需要等待的真实推理。** 不要一上来就让领导等 30 秒。

### 3.7 权限与账号体系

| 角色 | 权限 |
|---|---|
| 游客 | 门户、OCR、互转、翻译、TTS、ASR、语料集**只读**（限样例） |
| 注册用户 | 增加：导出个人结果、保存历史 |

| 管理员 | 用户与角色管理、数据集管理、模型与任务监控、审计日志 |

实现建议：**JWT + RBAC 自建账号体系**（服务部署在公网云上，**不应依赖校内认证服务**）；若学校愿意开放统一身份认证（CAS/OAuth）接口，可作为可选的第二登录方式，但**不能成为唯一路径**。

### 3.8 满文字体方案

- 把 `001A-Buleku-R.ttf` 用 `fonttools` 转为 **WOFF2**，并按全站用字**子集化**（通常能从数 MB 降到数百 KB）。
- 统一 `@font-face` 放在设计系统级别；竖排用 `writing-mode: vertical-lr; text-orientation: sideways-right`（现有 TTS 页面已跑通，直接复用）。
- 注意：**不要为字体引入第三方 CDN**（C3/P7）。

## 四、技术栈建议

### 4.1 总览

| 层次 | 推荐 | 备选 | 理由 |

## 五、部署与上线方案（实验室工作站 → 外网云端）

### 5.1 目录规范（代码 / 配置 / 数据 / 模型 四分离）

```
/opt/manju-platform/
├── docker-compose.yml          # 编排定义（进 Git）
├── .env                        # 环境变量（不进 Git，随环境不同）
├── .env.example                # 模板（进 Git）
├── config/                     # Nginx 等配置（进 Git）
├── data/                       # ★ 可变数据（数据库文件、上传缓存）
├── models/                     # ★ 模型权重（可挂载，可单独下载）
├── logs/                       # 日志
└── backup/                     # 备份输出
```

### 5.2 关键约定

| 项 | 约定 |
|---|---|
| 后端地址 | 前端**只使用相对路径** `/api/xxx`，由网关转发；**禁止**出现 `localhost:1000` 等硬编码 |
| 存储 | 统一走 `storage` 抽象层：`STORAGE_BACKEND=minio|oss|cos`，代码不感知具体厂商 |
| 字体 | 内置到前端构建产物，不依赖外网 |
| 数据库 | 只用 PostgreSQL，迁移时 `pg_dump/restore` 一把过 |
| 模型 | 权重放 `models/` 或对象存储，容器启动时按需拉取；**镜像里不打包大模型** |
| 时区/编码 | 统一 `Asia/Shanghai` + UTF-8，避免满文/拉丁字符乱码 |
| GPU | 通过 `docker-compose.gpu.yml` 覆盖文件开启 `deploy.resources.reservations.devices`，CPU 机器上自动跳过 |

### 5.3 上线清单（工作站 → 云端，按此执行）

```
【前置：第 1 周就启动，不要等】
-1. 买域名 → 买云服务器（≥3 个月）→ 提交 ICP 备案 → 等 10~20 个工作日

【云端首次部署】
1. 云端装 Docker +（如需 GPU）NVIDIA Driver / Container Toolkit
2. git clone 代码（或 docker load 镜像 tar 包）
3. 从工作站拷贝 .env，改域名、数据库密码、OSS/COS 凭据
4. 模型权重：从对象存储下载或直接同步（镜像里不含模型）
5. docker compose up -d
6. 初始化数据库（pg_restore 或建表脚本 + 种子数据）
7. 对象存储：`STORAGE_BACKEND=oss`，上传语料 / 图像 / 音频 / 字体
8. DNS 解析到云 IP + 配置 SSL 证书 + 验证 HTTPS
9. 验收：门户 + 6 大功能 + 登录 + 4 条推理链路全部跑通
```

> **工作站与云端共用同一份 `docker-compose.yml`**，差异全部收敛到 `.env`（`STORAGE_BACKEND`、域名、凭据、是否启用 GPU）。
> **这就是"工作站跑通即可上云"的实现方式**，也是约束 C11 的落地答案。

### 5.4 备份策略

| 对象 | 频率 | 方式 |
|---|---|---|
| PostgreSQL | 每日 | `pg_dump` 压缩包 → 对象存储，保留 30 天 |
| 对象存储数据 | 实时 | 开启版本控制 + 跨区域复制（可选） |
| 语料与标注结果 | 每日 | 增量同步到对象存储 + 快照 |
| 代码/配置 | 每次变更 | Git |
| 系统 | 每周 | 云快照 |

### 5.5 日常更新流程（上线后）

```
工作站改代码 → 提交 Git → 构建新镜像 → 推送到镜像仓库
    → 云端执行 docker compose pull && docker compose up -d
    → 数据库结构变更走迁移脚本
```

### 一句话总结

> 这个平台的本质是 **"一个统一门户 + 四个 AI 引擎 + 一套数据资产 + 一个登录受控的工作台"**，而**本期它是一台"演示机器"**——给领导看、开会用、验收用。
> **部署只有一条路：外网云服务器**（学校路线已作废）；**生产与批处理都放在工作站上，本期不规划**，所以容器化（Compose + 镜像 + 预生成内容包）是唯一交付形式。
> **服务器结论：买一台纯 CPU 云服务器就够，5,000 元以内绰绰有余。**
> **最省 → 轻量应用服务器 4核8G（含带宽+流量包，约 1,100~1,600 元/年）；要 8核16G → ECS 经济型 e 包年 ¥2,954.88（+200G 云盘 + 按流量带宽，合计约 4,150 元/年）。**
> **三个省钱开关：包年、带宽按流量、云盘只买 100~200G（大文件放 OSS）。本期不买 GPU。**
> **CPU 不是"只是慢一点"**，而是慢一个数量级，所以演示版真正的功夫在 **"预生成缓存 + SSE 进度反馈 + 演示模式开关"** 这三件事上——它们比买更贵的硬件重要得多。
> **"推理过程可视化"用一套统一的推理轨迹面板组件 + SSE 流式推送来实现**：既是本次需求的最大亮点，也顺手解决了"等太久"的问题，一举两得。
