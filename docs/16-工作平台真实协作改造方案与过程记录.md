## 0. 一句话结论

原来的工作台是 **mock 演示版**（数据在进程内存、不落盘），三个角色根本串不起来。
本次把它升级为 **SQLite 落盘的真实协作版**：标注员 / 审核员 / 管理员在同一份数据上闭环操作，
任务状态机真实流转，审核意见能回流到标注员，多 worker 下数据一致。

> 这也消除了 [11](./11-工作平台模块分析与初稿设计.md) §7 里"演示版不落盘、不上传"的差距——
> 现在 `/workbench/` 已经是"真"的，只是数据量仍是演示种子。

---

## 1. 背景：为什么原来"假"

旧版（11 §7 的演示版）把提交记录存在进程内存的全局列表 `_SUBS` 与会话里，三个硬伤导致"假"：

| # | 问题 | 具体表现 |
|---|---|---|
| 1 | **多 worker 各存一份** | 门户用 gunicorn **2 个 worker**，每个进程各维护一份 `_SUBS`——标注员提交落到 worker A，审核员刷新落到 worker B 就看不见，**闭环演示不出来** |
| 2 | **重启即失忆** | 内存数据随进程重启清空，状态全部回落初始 |
| 3 | **状态不回写、打回无去处** | 提交后任务状态不变，审核"打回"产生的意见无处安放 |

结论：**不落盘 = 三个角色串不起来 = 演示必穿帮**。正解是落库。

---

## 2. 目标

让三个角色（标注员 `zhang` / 审核员 `li` / 管理员 `wang`）像真实生产环境一样协作：

- 数据**落 SQLite**，换账号、换浏览器、重启门户看到的都是同一份；
- 任务状态机真实流转；审核意见能回流给标注员；
- 多 worker 下数据一致；越权与重复提交被拒。

## 3. 方案总览

- **新增 `modules/workbench/db.py`**：SQLite 数据层（`tasks` / `submissions` / `logs` 三张表），首次启动从 `mock.py` 注入种子（含**待审、已打回、可领取**三种状态，便于开箱即演）。
- **`mock.py` 降级为仅"种子源"**，运行时数据全部来自 DB。
- **蓝图 `__init__.py` 重写**：所有路由接 DB；移除 `_SUBS`；新增领取 / 指派 / 审核 / 详情 / 重置 / 切换身份等接口。
- **三角色视图**：标注员（待办 + 任务清单 + 打回意见）、审核员（待审队列 + 详情弹层）、管理员（指派 + 团队看板 + 操作日志）。
- **首页按角色显示真实待办**；演示版提供顶栏「切换身份」入口。

### 3.1 数据模型

```sql
tasks(
  id, kind, title, image, file, size, page,
  status, assignee, comment, created_at, updated_at
)
submissions(
  id, task_id, kind, title, user, payload JSON,
  attempt, status, reviewer, comment, created_at, reviewed_at
)
logs(id, ts, user, name, role, action, detail, task_id)
```

状态字典：`T_WAIT=待领取` · `T_DOING=标注中` · `T_REVIEW=待审核` · `T_PASS=已通过` · `T_REJECT=已打回`。

### 3.2 任务状态机

```
待领取 ──领取(claim)──▶ 标注中
标注中 ──提交(submit)──▶ 待审核
待审核 ──通过(review)──▶ 已通过（审核员可见，但不再可改）
待审核 ──打回(review)──▶ 已打回（意见回写 task.comment，标注员可见）
已打回 ──提交(submit)──▶ 待审核（attempt+1，标"第 N 稿"）
已通过 / 待审核 ──重复提交──▶ 拒绝（防重提）
```

每次状态变化都写一行 `logs`（谁 / 何时 / 做了什么 / 关联任务），管理员可在「操作日志」查看。

### 3.3 权限与边界

- `require_role` 装饰器按 `ROLE_LEVEL` 拦截（标注员 / 审核员 / 管理员）。
- 提交校验：`assignee` 必须为当前用户（未领取任务提交即自动认领）；**已通过 / 待审核不可重复提交**。
- 打回**必须填意见**；无意见被拒。
- 指派：仅管理员可调 `assignee`，触发状态回到「待领取」。

## 4. 三角色怎么用（用户视角）

- **标注员 · 张同学**：首页「我的待办」看到手上的活、被打回待返工、可领取数；任务清单能「领取」、提交；被打回时 OCR 页和首页**直接显示审核员意见**，改完可重提（第 N 稿有记录）。
- **审核员 · 李老师**：审核台待审队列 + 「查看详情」弹层（框内容 / 图片 / 置信度）；通过或打回，**打回意见自动回流标注员**。
- **管理员 · 王老师**：任务指派（把未指派任务派给谁）、团队看板（每人手头 / 待审 / 通过 / 提交 / 审核量）、操作日志。
- **演示便利**：顶栏「切换身份」下拉（仅演示版），无需反复登退；首页「重置」一键回初始局面。

## 5. 处理过程记录（踩坑与决策）

### 5.1 根因定位
读 `__init__.py` / `mock.py` / 模板，确认 `_SUBS` 在内存、gunicorn 2 worker 各存一份。结论：**落库是唯一正解**。

### 5.2 关键决策
- **选 SQLite 而非 Mongo/Postgres**：单机演示、零运维、文件即库、`.gitignore` 排除 `data/` 即可。
- **种子从 mock 注入**：保留演示底稿（真实语料切片的古籍图 / 句对），只把"假状态"换成"真状态机的初始值"。
- **移除 `_SUBS` 全局内存列表**：所有读写走 `db.py`，从根上消除多 worker 不一致。

### 5.3 踩过的坑（均已修复）
1. **提交号撞号**：原按"该任务的提交次数"编 `S-...-001`，两个任务各自首次提交算出同一号 → 主键冲突。改为**以全局条数为基数 + 循环兜底**保证 `id` 全局唯一。
2. **模板改了不生效**：gunicorn 默认把 Jinja 模板缓存在内存，只改 `.html` 不重启看不到变化。所有模板改动后必须 `systemctl --user restart manchu-portal`。
3. **`write_to_file` 看似成功却没落盘**：一次整体覆盖 `index.html` 返回 success，但随后 curl 仍是旧页——磁盘实际未更新（疑似会话内写入未提交）。后用 `grep` 核对磁盘关键词 + 硬重启验证，确认最终落盘。
4. **越权与重复提交**：补 `submit_task` 状态校验（已通过 / 待审核拒绝重提）、`assignee` 校验；打回必填意见。
5. **多 worker 一致性**：数据全部走 SQLite（文件级锁），2 worker 天然共享同一份，验证通过。

### 5.4 验证方法与结果
- **Flask test client 端到端**：覆盖三角色页面可达性、403 越权（标注员访问审核台 / 管理员页）、领取→提交→审核→打回→返工闭环、指派、打回无意见被拒、重复提交被拒——全部符合预期。
- **真实 HTTP 多 worker 一致性**：curl 多次跨 worker 访问首页均 200；完整走一遍 `ja044`：领取 → 提交 → 审核员打回（带意见"第2列满文需复核"）→ 标注员 OCR 页 / 首页出现该意见、待办出现"被打回待返工"、DB 状态同步为已打回、`attempt` 递增。
- **结果**：全部通过；演示数据最后 `reset_db()` 回到初始局面。
