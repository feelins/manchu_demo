## 0. 一句话结论

`06语料集/` 目前**只有"分类壳子 + 4 个样例文件"，不是可运行的模块**：5 个分类里 3 个是空目录，唯一成规模的数据是 4.5 MB 的满汉平行语料（98,038 行 / 49,019 句对）。

但**本机 `/home` 下有充足的原始数据可供切片展示**：真实古籍图 17,198 张（带满文标注）、合成图 173,170 张（带标注）、语音对齐数据 2,424 条（wav + 文本 + TextGrid）。
即"对外只展示一部分"这个要求**数据侧完全满足**，缺的是口径确认与授权确认，不是数据本身（详见 [3.1](#31-可展示样例切片已在本机定位)）。

语料集要做的事不是"把数据搬到网页上"，而是三件：**把数字核实清楚 → 给每类语料一个可浏览的样例切片 → 建立元数据与申请/导出通道**。

> **2026-09-25 进度**：三项均已落地。数字**一律按本机实测值填入**（需求文档与实测不符的以实测为准，口径差异写进 `note` 与元数据），首页 5 张卡与 `/corpus/` 总览已全部有数；使用人如需改用其它口径，改 `config.py` 与 `modules/corpus/__init__.py` 两处即可。

### 2.1 平行语料的真实形态（已核实）

```
$ wc -l "all1+2+3.txt"          → 98037
$ head -6
an -i gisun de amtan be sara bithe -i xutuqin     ← 拉丁满文
```

### 两个必须注意的点

1. **语音数据一身二用**：`0603 语音合成数据` 与 `0604 语音识别数据` 指向的是**同一批 wav**（0604 目录名已注明"反向使用语音合成数据"）。
   所以页面上应是**一类数据、两种用途**：TTS 侧展示"文本 → 音频"，ASR 侧展示"音频 → 文本"，共用同一批切片，不要重复计数。
2. **合成图标签带 BOM**：`manju_170k/*.txt` 以 `\ufeff` 开头，直接读取会在首词前多一个不可见字符，**切片生成时必须 strip BOM**（真实古籍的 `images_clean/*.txt` 无此问题）。

## 3.2 展现维度设计：每类语料"展示什么"

### 通用元数据维度（每类卡片必备，解决"数字口径"问题）

| 维度 | 说明 | 例 |
|---|---|---|
| 数据类别 | 对应 0601~0605 的哪一类 | 满文 OCR 训练数据（真实古籍） |
| 规模 | 条数 / 句对数 / 时长 | 7,739 行（训练索引） |
| 形态 | 文本 / 图像 / 音频 | 图像 + 满文标注 |
| 版本 | v8、`ancient_4k_v7` 等 | ancient_4k_v7 |
| 采集/生成方式 | 扫描古籍切分 / 字体合成 / 录音对齐 | 古籍扫描后切分 |
| 标注类型 | 传统满文 / 拉丁转写 / 音素对齐 | 传统满文（人工校对） |
| 授权范围 | 公开展示 / 需申请 | 仅展示切片 |
| 统计日期 | 口径锁定时间 | 2026-09-25 |

> 这 8 项写不全，就别在首页填数字。
> **2026-09-25 已按实测值填入 5 项**，各类元数据写在对应的 `static/corpus/<类别>/index.json` 里；
> 缺失的字段（如授权状态、古籍种/套数）补齐后，同步更新卡片 `note` 即可。

### 分类专属展示维度

**① 平行语料**：三栏对照 —— `汉文` ｜ `拉丁满文` ｜ `传统满文（反写，标注为转写结果）`
附加：句对序号、来源文献（若后续补上）、字数、检索框（支持汉文 / 拉丁 / 满文三种输入）。

**② OCR 图文**：`图像缩略` + `满文标注` + `来源类型（真实古籍 / 合成字体）`
附加：图像尺寸、档号（如 `ja08027`）、可叠加"模型识别结果 vs 人工标注"对比（这一步很有说服力，且复用现成的 OCR 服务）。

**③ 语音**：`音频播放器` + `拉丁文本` + `波形/频谱`
附加：时长、采样率（24 kHz）、音素数、对齐文件（TextGrid）可视化；**同一批数据在 TTS 页签显示"文本→音频"，在 ASR 页签显示"音频→文本"**。

## 4. 要做的部分：功能拆解

按"对外展示 → 对内管理"分成 7 块：

### A. 数据总览卡片（P0）
首页 + `/corpus/` 顶部：5 张卡的**真实数字**。
硬要求：每个数字都要有"统计口径 + 统计日期 + 数据来源路径"，鼠标悬停可看口径说明。
**数字一律取实测值，口径差异写进 `note`；没有实测依据的不要估。**（2026-09-25：5 类全部有实测值，已填入）

### B. 分类目录（P0）
对应 5 个分类，每类一张卡：名称、规模、形态（文本/图像/音频）、样例入口、是否开放申请。
`0603` / `0604` / `0605` 三类目前空目录，卡片上要**如实标注"数据待补充"**，而不是隐藏。

### C. 样例浏览（P0，是 02 方案明确要求的"20~50 条"）

切片来源**已在本机定位完毕**，详见 [3.1](#31-可展示样例切片已在本机定位)：

- **平行语料**：抽 30 句对，双行/三栏对照（拉丁满文 / 汉文 / 满文反写）；
- **OCR 图文**：真实古籍 8~10 张 + 合成 8~10 张，均为"图 + 满文标注"配对，并可叠加快 OCR 识别对比；
- **语音**：v8 中挑 8~10 条 1~3 秒短音频（TTS / ASR 两种用途共展示）。

> 注：`06语料集/0603` 目录是空的（批注"需要邵老师提供"），但**本机 `Manchu_data_v8` 已有 2,424 条可用**——
> 缺的是"官方交付的数字"，不是数据本身。展示前需确认授权，数字仍建议等官方口径。

切片已由 `scripts/make_corpus_samples.py` 生成到 **`static/corpus/`**（见 3.1）。
**切片入库（742 KB），原始全量数据不入库**；脚本等距抽样、结果确定，重跑可复现。

### D. 检索（P1）
对切片做关键词检索：支持汉文、拉丁满文（含 `k'`/`ng` 等）、传统满文三种输入。
规模小（每类几十条），**SQLite FTS5 或直接内存过滤即可**，不必上 ES。

### E. 元数据与版本管理（P1）
每类语料的元数据：来源、版本（如语音 v1~v8）、标注方式、许可证/授权范围、条数、时长或字数、生成脚本。
这一块解决的是"14,242 与 2,424 哪个是真的"这类问题——**版本口径必须写进元数据**，否则每次对外报数都会重新争论一遍。

### F. 导出与申请（P1/P2）
- 规范化导出：提供拉丁 / 传统满文两种转写的导出（复用 `manju-rules.js` 规则）；
- 全量数据**不直接下载**，走"申请 → 审核 → 授权"流程（与阶段 5 的 JWT + RBAC 一起做）。

## 5. 技术设计建议

| 依赖 | 无模型服务依赖 → **不需要新增端口**，是六个模块里唯一纯数据模块 |

## 8. 风险

| 风险 | 说明 | 应对 |
|---|---|---|
| 数字口径不一致 | 需求文档数字与本机实测多处不符（OCR、ASR、古籍总量） | **一律以实测值填入并注明口径**（2026-09-25 已执行，5 张卡全部有数）；使用人要对齐需求文档口径时，改 `config.py` 与 `modules/corpus` 两处即可 |
| 多版本混淆 | 语音 v1~v8、OCR 多版训练产物并存，极易重复计数 | 元数据里写死"对外口径 = v8"，并在页面注明版本 |
| 全量数据入库 | 4.5 MB 语料尚可，但语音数据量大，进仓库会拖垮部署 | 只进切片，全量走对象存储 + 申请下载 |
| 转写误差被当原文 | 平行语料是拉丁转写，反写满文不等于原始文献 | 页面明确标注，必要时只展示拉丁 + 汉文双行 |
| 合规 | 古籍与语音数据的使用授权未明确 | 申请流程 + 授权说明前置，先小范围展示切片 |
